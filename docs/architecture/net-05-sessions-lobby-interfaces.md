## 1. Product intent, scope and acceptance
Catalog scope: **Match/session/lobby abstractions; optional external backend integration**. Catalog acceptance: **"Criar/join/leave, reconexão e falhas previsíveis sem SaaS obrigatório."** The first future functional proof must include two separately authorized client identities and one local dedicated NET-02 server, create/list/join/leave a lobby, allocate/start/complete a match, drop/reconnect a connection and reject unauthorized access under explicit failures. **A lobby join is not admission to a game server, and a server allocation is not a valid identity credential.**

**Local-first meaning:** a reproducible localhost process and explicitly scoped developer/test identity provider with no paid account, SaaS, public internet, Kubernetes or externally hosted relay. Production authentication still requires secure, reviewed identity proof; an unsigned "guest" token is **never** accepted on public endpoints. Guest mode may exist **only on loopback/isolated test harness** with privileged local configuration and test-only keys; no silent transition into production.

## 2. Distinct bounded authority domains
| Area / owning module | Sole authority | NET-05 boundary |
|---|---|---|
| NET-05 | player session binding, short-lived join ticket issuer/validator policy, lobby/party lifecycle, presence visibility, invites, match queue/allocator interface, discovery profile and recovery policy | does not own game simulation, transport crypto or global billing |
| NET-01 *(formal prerequisite)* | authenticated secure connections, UDP/QUIC/WebTransport/RTC/WSS capability, packet encryption, reconnection transport and network reachability/NAT/ICE/STUN/TURN flow | NET-05 requests connectivity outcomes and credential references, never custom relay/TLS/UDP implementation |
| NET-02 *(formal prerequisite)* | headless authoritative match process/instance state, actor/role/commands and actual game admission, lifecycle/health and process drain | NET-05 reserves/allocates; **NET-02 must revalidate join ticket, role and match lease independently** |
| NET-03 | per-recipient state/field authorization and snapshots | no hidden player state disclosed in public lobby cards or "spectator" auto-join |
| NET-04 | client prediction, session/world epoch correction and jitter | reconnect invalidates old history, does not turn a lobby token into a gameplay ACK |
| NET-06 | abuse telemetry, hostile auth/replay/fuzz/brute force/DoS safeguards, privacy and incident response | policy integration, no duplicate DDoS core or claim "JWT makes cheating impossible" |

Only **NET-01 · NET-02** are formal catalog edges; other modules are integration boundaries, not new DAG dependencies. NET-06 research **follows** NET-05, so this proposal must not claim approved anti-abuse runtime.

## 3. Four separate state machines
- **Identity session (`AuthSessionV1`):** `UNAUTHENTICATED -> AUTHENTICATING -> ACTIVE -> REFRESH_PENDING -> EXPIRED / REVOKED / LOGGED_OUT`. An authenticated identity does not imply lobby membership, match allocation, or actor ownership. Auth issuer/provider must be pinned by game policy; OIDC subject identifiers are provider-scoped, not globally trusted user IDs.
- **Party (`PartyV1`):** `CREATED -> INVITING -> FORMING -> QUEUED -> RESERVED -> MATCHED -> DISSOLVING -> CLOSED`; leader/officer/member roles, max members, party constraints, atomic membership reservation, role transfer and kick/ban. Leader departure requires deterministic role transfer under accepted policy or close/leave. Party can exist without match and should not imply persistent friendship or long-term clan identity.
- **Lobby (`LobbyV1`):** `CREATED -> OPEN / INVITE_ONLY -> LOCKED -> ALLOCATING -> READY_TO_LAUNCH -> LAUNCHED -> DRAINING -> CLOSED` plus typed `FAILED`. Host/owner is **lobby administration**, not server gameplay authority. Controls for invite, readiness, slot reservation and content compatibility; no implicit server start from one client request.
- **Match session (`MatchSessionV1`):** `REQUESTED -> RESERVED -> SERVER_ALLOCATING -> SERVER_READY -> JOIN_AUTHORIZING -> ACTIVE -> COMPLETING -> CLOSED` with `ALLOCATION_FAILED`/`RECOVERING`. Server NET-02 has its own process/match lifecycle and can reject a NET-05 reservation if lease expired, config mismatch, server at capacity or ticket invalid; matchmaker match assignment may not create actual server session.

All transitions require expected revision/idempotency key, credential capability and current generation. Never treat a duplicate asynchronous callback, stale invitation or rejoin timeout as new assignment. Compensating cancellation releases reservations and invalidates ticket generation; avoid dangling match slots after retry.

## 4. Create / join / leave protocol (conceptual)
1. Client local/authenticated identity obtains `AuthSessionV1` by approved provider. Public native/Web auth flows should follow [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) including Authorization Code with PKCE for public clients where OIDC is applicable; refresh tokens stored by platform secure storage rules, no plaintext source file or logs.
2. `CreateLobby(Principal,Policy,IdempotencyKey)` checks allowed title/metadata, max size, invite/role/visibility, content/build compatibility, administrative quota and revision. Public listing projects a **minimal allowlisted metadata view**, never exposes session tokens, full IP, friends' private presence or connection debug info.
3. `InvitePlayer` issues a short-lived, scoped, cancelable invitation to an explicitly allowed recipient (or bounded single-use code under policy). The *invitation* is not itself a session credential or game join entitlement. Block lists/age/privacy/moderation/banned principals override invitations.
4. `JoinLobby(Identity,InviteOrDiscovery,ExpectedGeneration)` atomically checks account, privacy, lobby state, capacity/reservation, version and signature, then writes membership and emits a typed join receipt. Join/leave operations have idempotency and race-safe compare-and-swap; duplicate joins cannot consume two slots or bypass bans. Presence update distributed best effort with lease/TTL, **not** a certificate of real online status.
5. Optional `MatchSearch` consumes explicit game/region/ping/party/skill policy and gives a bounded queue ticket; matchmaker algorithm is **pluggable** and can simply select a local ready server/lobby for the baseline. Search response is not match admission, and queue times depend on players; no false instant-result guarantee.
6. `ReserveServer -> AllocateServer -> IssueJoinTicket` uses NET-02 known ready/healthy server lease, actor/role, match ID, world/server allocation generation and allowed content version. Transfer signed, **audience-bound, short-lived, optionally one-time server-confirmed** ticket over NET-01 authenticated channel; NET-02 independently verifies signature, issuer, audience, world/match lease, actor, account bans and used nonce/connection binding. Ticket replay across matches/servers/roles must fail closed.
7. `LeaveLobby/LeaveMatch` checks actor/session authority, atomically releases membership and reservation under expiry fence, sends redacted event, updates readiness, and does not automatically destroy other players' active match. Distinguish voluntary leave, disconnect, kicked, server drain, session expiry and host disconnect. GAME-04 owns economy/score receipts; "leave" is not game save success.

## 5. Reconnect, host migration, NAT and recovery
- Connection disconnect ≠ identity logout ≠ lobby leave ≠ match abandoned. A bounded reconnect lease with role/actor/match epoch and capacity reservation can allow reconnect. Require fresh NET-01 authenticated transport, current NET-05 session/refresh and NET-02 reauthorization. Issue **new** short-lived ticket/generation, revoke old nonce, invalidate NET-03 baseline and NET-04 predicted history. Fail closed after expiry, ban, match closure or world/source mismatch. Grace/backoff/jitter values **TBD**, not global constants.
- **Host migration:** a dedicated server's authoritative state cannot be moved merely by changing lobby owner. Initial implementation supports **no transparent live migration**; on failure return `MATCH_RECOVERY_REQUIRED` or documented restart from DATA-04 committed checkpoint and fresh NET-02 process allocation. FUTURE host migration needs epoch fencing, validated durable state/side effects, atomic allocation transfer, replay dedup and external consistency. P2P host-authority migration is separate and not acceptable by default for economy/competitive gameplay.
- **NAT:** Server discovery can yield an authenticated logical server endpoint/ref and NET-01 transport capabilities. Direct IP/port enumeration may expose players' IPs, so prefer dedicated server addresses and privacy profiles. [ICE RFC 8445](https://www.rfc-editor.org/rfc/rfc8445.html), [STUN RFC 8489](https://www.rfc-editor.org/rfc/rfc8489.html) and [TURN RFC 8656](https://www.rfc-editor.org/rfc/rfc8656.html) are connectivity methods, not a substitute for auth/anti-abuse; STUN alone is not universal NAT traversal, TURN is relay with bandwidth/operating cost. NET-01 provides credentials/packets, NET-05 only requests/authorizes discovery and relay policy; no secret logged, no user-provided arbitrary TURN/URL SSRF.
- **Failure semantics:** retryable timeout/network/issuer outage, hard deny auth/expired/revoked/ban/role, server capacity, allocation lease/cost/unavailable provider, schema/world mismatch, data consistency conflict, rate/exhaustion. Every response is typed with bounded retry/backoff, no accidental fallback to a public insecure guest or paid cloud provider.

## 6. Security: authn vs authz vs capacity, session-ticket model
A secure session protocol should reject blind JWT acceptance. [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html) calls out algorithm confusion, token type/cross-JWT confusion and untrusted key URLs. Token validator pins issuer, audience, explicit typ, allowed algorithm, key ID through configured key registry only, iat/nbf/exp with bounded skew, game/match/server/actor/session generation, nonce/jti and revocation/rotation. Signatures alone do **not** prove one-time use, current revocation, party role or game authority.

- Use server-held single-use nonce/jti state or binding to NET-01 secure channel/connection where a reviewed mechanism permits; choose replay-store consistency at deployment. [RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html) DPoP is an **HTTP OAuth proof-of-possession reference**, not a claim that DPoP automatically secures UDP/QUIC game datagrams. Signed bearer ticket over authenticated transport needs short expiry/revocation and server replay control.
- Separate least-privilege scopes: lobby administration, membership, invitation, spectator, match join, relay access, server ops and game actions. No token should be an unrestricted admin/game state bearer. Match tickets cannot be used at lobby OAuth/admin endpoints and vice versa. A platform Steam/EOS identity proof alone does not confer Stormline role/character ownership.
- Protect spam, enumerable lobby IDs, brute-force invitation codes, alias collision, block-list circumvention, rejoin/kick evasion, simultaneous joins filling slots, connection amplification, provider callback replay, open redirect, SSRF arbitrary join URL, overlong/chat/presence metadata and cross-account leakage. Follow NET-06 threat model and future fuzz/rate/abuse tests. Do not store passwords, external provider raw tokens or PII in publicly inspectable scene/asset files.
- Privacy profile: opt-in presence, friends-only/discoverable/private lobbies, anonymous/nonenumerable join metadata, region and ping approximations only if policy allows, explicit retention/TTL, report/block controls, log redaction, game minors policy and LGPD/other applicable regulation by future legal review. Unknown identity or visibility => deny.
- Ops/admin/Editor/CLI/MCP requires a **different authenticated administrator capability** and expected revision, cannot join a player's private lobby invisibly, impersonate accounts or trigger cloud allocation/billing without explicit operator approval. Cloud credentials never go in client binaries.

## 7. Technology and deployment tiers
**NECESSARY (future first code after approvals):** single local process-backed or self-hosted lobby/session service, explicit local test-identity issuer **loopback only**, secure normal public auth for production profile, one manually started NET-02 server, named lobby create/join/leave, finite tickets and restart/resume failure semantics, no third-party service mandatory. Use DATA-04 or approved store for persistent production membership/nonce consistency; developer in-memory mode not automatically crash durable.

**IMPORTANT (future):** role privacy/presence, moderated invites, parties, typed matchmaking reservations, lease renewal, redacted discovery, reliable reconnect with ticket rotation, native/Web platform auth and voice/text as *separate* game UI/social modules. **FUTURE:** cross-region matchmaking and migratable server fleets, QoS multiprovider ranking, game-specific anti-smurf, account linking, Agones allocation, Steamworks/EOS features and external orchestration. No v1 release class, latency, queue time, multi-region cost or monetization adoption in P00.
