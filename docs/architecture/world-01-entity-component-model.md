## 3. Identity: permanent GUID versus transient generational handle
- `WorldIdentityV1`: ProjectId, WorldId (stable logical ownership), world-instance/epoch (fresh per load/clone), revision, authority/access role and independent world capacity quotas. World clone/rollback/remount can create a new epoch; stale instance handles must not regain validity.
- `EntityHandleV1`: runtime-only structured `{world_instance_epoch, slot_index, slot_generation}` (exact bit packing TBD) with invalid sentinel, local to one loaded world. Allocation from free slots increments **generation** before reuse; on generation exhaustion **retire that slot or otherwise provably avoid ABA**, never wrap into an old live handle. World destruction invalidates all handles, even if numeric slot/gen reused in a different world instance. No pointer/reference to component memory persists across structural moves.
- `EntityGuidV1`: DATA-02 stable logical identity (e.g. 128-bit UUID candidate, actual format TBD) persisted in DATA-04 scenes and authoring transactions. During load, `EntityGuid` is resolved to current `EntityHandle` under project/world source revision; missing/unloaded/migrated/destroyed result is typed. Cross-world references require explicit contract/proxy, **never** raw numeric handle lookup in another world. Conflict policy for duplicate GUID import must reject or remap with provenance and reference fixup transaction, no silent aliasing.
- Handles and persistent IDs are different: *save GUID only*, not slot/generation memory; authoring/API returns stable GUID plus runtime ephemeral handle when capability allows. Strong references to unloaded scenes/prefabs are data references with resolving status, not a dangling pointer.
- Destruction is a **staged state transition** `ALIVE -> DESTROY_REQUESTED -> TOMBSTONED -> RETIRED`; transition fence/borrow guards prevent use-after-free. Destroying twice safely yields typed `ALREADY_DELETED` or idempotent receipt. Components detach once, observers/queries see a clear epoch, cleanup uses owner-supplied destructors where verified and no callback reentrancy against the mutating registry. Late GPU, PHYS and NET references are invalidated by generation and epoch. Tombstone semantics for persistence and undo live in DATA-04; ECS runtime should not become permanent history database.

## 4. Component schemas, reflection and robust type contracts
- Each component has `ComponentTypeIdV1` that is stable across recompilation, **not** `typeid().hash_code()`, compiler-dependent mangled string or ephemeral C++ RTTI address. `ComponentSchemaV1` includes version, editor-facing field names/types/units/ranges, defaults, mutability, deterministic/replicated/serialized flags, permissions, migration hooks (DATA-04 owner), constructor/destructor/copy/move/align facts, serialization constraints and checksum.
- Compile-time type traits or **source-generated metadata** are portable baseline. C++26 static reflection P2996R13 is in the standard working draft, but **optional** for build compilers until Windows/Linux/macOS/Emscripten support proved; must not require unpublished compiler forks/UB. Existing EnTT meta/Flecs reflect capabilities are candidate adapters, not stable public engine types.
- `ComponentTypeRegistryV1`: registers stable TypeId+schema version and checked byte size/alignment/construct+destruct semantics. Colliding IDs, incompatible reload, double register or unknown migrations fail before world mutation. No user-controlled code/class constructor invoked during untrusted import, no arbitrary pointer/native memory script reflection.
- Separate **runtime transient components**, *persisted authorable component state* and *replicated authoritative component subset*. Handle-based runtime cache is not serialized or replicated as raw bytes. Endianness, padding, `bool` size, pointer fields, dynamic arrays and C++ vtables forbid `memcpy` serialization; pass semantic fields via DATA-04 adapters with explicit schema migration.
- Headless server can carry gameplay components without GPU/Canvas/Shader or imported editor UI. Reflection exposes allowlisted fields, documentation and edit diff via Editor/CLI/MCP but never object memory addresses, sensitive secrets or privileged authority.

## 5. Storage policy: archetype tables + sparse candidates, measure before adoption
- Primary candidate **chunked archetype/SoA or table-layout ECS** for hot predictable per-frame component iteration (Position/Velocity/Health), with a **sparse-set storage tier** for rare/high-churn components, conditional on actual benchmarks. Flecs archetype/queries and Bevy Tables/SparseSet serve research references. EnTT uses sparse-set registry. **This is a research hypothesis**, not locked runtime data layout and not an adopted library. Poorly managed archetype fragmentation, frequent structural transitions and component churn can make archetypes worse.
- `StoragePolicyV1` chooses `TABLE_DENSE` or `SPARSE_STABLE` per registered type after instrumentation. Migrating a component's storage at runtime changes location/epoch and invalidates borrows, not stable EntityGuid. Source data and type metadata remain independent of ECS layout. No raw EnTT/Flecs entity or query type crosses public SDK, serialization or ABI.
- Bound archetype combination count, entity count, component bytes/alignment, chunk page size, query cache entries, transient command buffers, memory/arena pressure and empty archetype pruning policy. Bevy docs highlight that archetypes may persist even when empty; do not assume fixed memory usage or unlimited combinations.
- For hot, high-churn, owner-specified workloads compare at **equal query result correctness**: archetype transitions/cache/sync barrier cost vs sparse insertion/removal/random access and row iteration, including memory peak and invalidated pointers. No unmeasured “millions of entities/60 FPS” claim.

## 6. Queries, stable iteration, borrowing and concurrent access
- `EntityQueryV1`: typed include/without/optional component filters, changed-since-version, world/subset scope, read/write access contract and iterator snapshot epoch. Query match set can be cached but cache must invalidate on schema registration/archetype/membership changes. A query cannot safely keep a mutable raw component pointer across a structural change.
- **Default iteration order is unspecified** for performance; deterministic gameplay simulations that require order must request an explicitly **stable EntityGuid/EntityHandle sorted snapshot**, with measured sorting cost and no promise of stable order from dense swap-remove. Parallel query reduction must declare associativity/fixed reduction order for deterministic gameplay if order matters.
- Borrow enforcement: resource/component read-many vs write-exclusive access, scheduling via CORE job owner and `SystemAccessV1` footprints; no concurrent mutation while another thread iterates the same storage. A query view is valid for one world/query epoch, invalidated after an applied structural command/fence, not a persistent pointer.
- Version/change tracking must distinguish `ADDED`, `MODIFIED`, `REMOVED`, `DESTROYED` with source tick and ability to handle tick wrap/stale snapshots. Do not expose a false `Changed` if only touched mutable reference; define whether write barrier, explicit Dirty flag or actual old/new diff is used and test. Query and event notifications receive immutable receipts, no unbounded reentrant observer cascade.

## 7. Deterministic deferred structural changes and safe tick boundary
- During world update, jobs and queries **enqueue** bounded `EntityCommandBufferV1` operations (create/destroy/add/remove/set schema-valid fields). CORE scheduler establishes a barrier and WORLD-01 validates expected WorldEpoch and EntityHandle generations, per-command stable issuer+sequence/tick; deterministic merge order is **explicit** for systems requiring fixed replay, rather than nondeterministic worker completion.
- Apply a staged `PREPARE -> VALIDATE -> COMMIT -> PUBLISH` at safe boundary. Batch grouping reduces random sync points and pointer invalidation. Unity's Entities docs show structural changes cause synchronization points; Flecs defers/stages ops similarly. On validation error or OOM, owner needs a defined **atomicity unit** (per transaction or per command buffer with rollback) and a typed partial receipt; no half-updated live entities with broken refs.
- Conflicts: destroy wins only according to explicit priority; add/remove same TypeId in one buffer has ordered semantics, duplicate create GUID error, double-destroy idempotent, referenced entity deleted earlier in frame -> invalid with typed reason. Cross-world command denied; network clients cannot directly issue privileged destroy/create, even if they guess a GUID.
- Readers see last committed snapshot until publish and safe epoch. Change streams bounded/retained per subscriber; consumers GFX/PHYS/NET receive `EntityLifecycleReceiptV1` and validate world/revision/owner, not an executable callback or unsynchronized pointer.

## 8. Integration lifecycle with DATA-04, WORLD-02 and future networking
- Editor `StageEntityEditV1` with ProjectId/WorldId, expected DATA-04 revision and checked component fields, validated diff; `CommitEntityTransaction` updates DATA-04 source journal and ECS runtime as distinct phases with explicit reconciliation and crash recovery. Save/reopen must preserve stable GUID/field schema, but runtime generation/slot is re-assigned and references are resolved.
- WORLD-02 owns parent/child hierarchy and prefab composition, **not WORLD-01**. WORLD-01's entity knows no “parent index” except optional typed component data supplied by WORLD-02. Destroy parent does not blindly recursively destroy all children unless WORLD-02 authorizes a policy and sequenced transaction; prefab stable references must not accidentally point to recycled handles.
- WORLD-03 spatial streaming can unload entities via lifecycle command receipts; unloaded is not identical to destroyed permanent, and when reloaded DATA-04 persistent GUID resolves to fresh handles. Authority/world epoch and stream source epochs handle slow jobs. World-relative transforms belong CORE-05; root motion from TWO-03 remains proposal until authoritative PHYS/WORLD owner acceptance.
- Network gameplay/replication owner defines id remap, authority and interest, does not replicate C++ pointers or raw world slot. A malicious remote client cannot spoof local EntityHandle, mutate server-owned Health/Inventory or supply unbounded serialized ComponentType schemas.

## 9. AI-native authoring, security and validation
- Semantic **readonly** `InspectEntity`, `ResolveEntityGuid`, `ListComponentSchemas`, `QueryEntitiesPage`, `PreviewEntityDiff`, `InspectEntityLifetimeReceipt`, `GetEcsDiagnostics`. Every response project/world scoped, least-privilege, paginated and metadata redacted; no full arbitrary memory dump/PII.
- Mutations `StageEntityCreate`, `StageComponentPatch`, `StageEntityDestroy`, `ValidateEntityTransaction`, `CommitEntityTransaction`, `CancelEntityOperation` through DATA-04 journal/CAS and world-safe command buffers. Validate project role, component type allowlist, field constraint ranges, object references and content rights; quotas limit per-tick entity creation and graph/schema cache thrashing.
- Reject hostile editor plugin/schema registration, dynamic native type import, unbounded reflection recursion or callback scripts, file paths, external URLs, cross-project ID leaks and resource exhaustion. Unknown type ID / schema version -> quarantine/recovery, not blind reinterpret of bytes. All exported state must have legal content rights and per-field secrecy policy.
- Runtime memory sanitizer, fuzz, race detector, native Web compile/ASan/TSan where supported and deterministic replay oracles are FUTURE. **No tool / ECS library installed now.**

## 10. Optional R&D: STLG — Stormline Temporal Lifetime Guard
A **PROVE-OR-DROP** static/dynamic handle lifetime checker that records an entity's world/slot/generation and source revision at materialization and catches deferred stale accessor uses across job barriers, undo and scene reload. Baseline is rigorous generational handle+epoch validation; STLG's extra maps/diagnostics must demonstrate repeatable real defect capture without CPU/memory harm. No novelty/performance proven and not a mandatory development prerequisite.
