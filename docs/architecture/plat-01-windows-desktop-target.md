## 1. Product objective and proof boundary
Windows is a mandatory desktop target for both Stormline **Editor** and exported **games** under NLE-D017. Catalog acceptance: **"Build e smoke test em hardware Windows definido."** This architecture specifies *future* native Windows process/window/input/RHI presentation/audio integration and package capability boundaries for reproducible hardware smoke. P00 delivers **no Windows binary, source code, packaged installer, signed executable, GPU screenshot, hardware test, measured compatibility or deployed engine**. Windows Editor and game exports have separate startup/permission/asset and packaging profiles; a successful developer build does not prove that a clean Windows machine runs a distributable.

### Windows support policy is intentionally NOT frozen
- Current minimum OS build/edition and servicing window require owner-approved support matrix based on current servicing and actual devices. **Candidate reference**: supported Windows 11 x64 client with latest patch/SDK; Windows 10 mainstream ended **2025-10-14**, LTSC/ESU exceptions need separate support/security policy; no blanket Windows 10 support claim. Future Windows ARM64 target is an **optional candidate** to validate with toolchain, GPU, native DLL and x64 emulation, not silently required by NLE-D017.
- Test Windows 11 supported SKU/build and targeted desktop GPU tier, Intel/AMD/NVIDIA hybrid laptops, high DPI/refresh and power/sleep, clean user account without dev tools. The exact OS SKU/build, minimum GPU feature and QA hardware bill of materials must be ratified separately. Never assume a Windows SDK version changes the operating system API availability.
- Engine runtime and Editor shipping lifecycle/installer/updates are owned by **BIZ-03**; PLAT-01 specifies Windows-specific capabilities and distribution artifacts and provides a validated package *input* contract, without auto-publishing, writing an updater or acquiring signing identity.

## 2. Formal dependencies, transitive owners and separation of concerns
Formal DAG edges **exactly GFX-01 + GAME-01**:
- **GFX-01** is sole RHI/adapter/device/swapchain generation owner. PLAT-01 offers Windows window/presentation surface/capability bridge, display/DPI/HDR/occlusion and native host conditions to GFX-01. It cannot choose global Vulkan vs D3D12 stack for the whole engine or expose native GPU handles to MCP. ADR-0014 remains PROPOSED; GPU device-loss and reload semantics require real owner receipts.
- **GAME-01** is sole semantic InputActionMap/DeviceEpoch/PlayerSeat/context/tick owner. PLAT-01 and transitive CORE-01 normalize Win32/SDL host device state and pass typed events; PLAT-01 cannot create an independent gameplay action mapper, global raw keyboard logger or unrestricted input injector. ADR-0042 remains PROPOSED.
- **CORE-01 transitive**: process lifecycle, exactly ONE SDL3/Win32 event pump and host thread, window/focus/suspend/high-DPI epochs, opaque native window handles and optional headless. PLAT-01 is a Windows-specific **adapter/capability implementation at the host boundary**, not a second OS authority. A Win32 bridge is used only if SDL3 cannot express an explicit requirement; all callbacks go through CORE-01.
- Other **integration owners (not new formal dependency edges)**: GFX-02 shader compile; GFX-03 render graph; GFX-07 color management; AUD-01/AUD-02 sample mixing/device graph; CORE-04 tick; CORE-06 local diagnostics; DATA-01 VFS / DATA-05 cooking; GAME-03 text/UI; EDIT editors; PLAT-02 Linux / PLAT-06 macOS; BIZ-03 installer/update/rollback; AI-01/AI-06 via MCP. Windows adapters cannot overwrite their public API schemas or implement assets and signing on their behalf.

## 3. Proposed Windows process and event architecture
```text
Editor.exe / Game.exe [separate signed/unsigned dev targets]
   |
CORE-01 process host + exactly one main-thread SDL3/native event pump
   |   [window creation, focus, DPI/size, display/hotplug, suspend, exit]
PLAT-01 Win32 bridge and WindowsCapabilitySnapshotV1
   |                    |                              |
GFX-01 Windows surface  GAME-01 typed device events    AUD-01 owner port
GPU present lifecycle   no semantic remap in adapter   OS audio backend
   |                    |                              |
GFX RHI device/gen      InputActionFrame/TickId        bounded audio callback
   |                    |                              |
CORE-06 bounded local diagnostics and source/build correlation
   |
BIZ-03 Windows package/export integration (separate authority)
```
Run main window/event pump on supported UI thread, don't pump from worker. SDL3 `SDL_PumpEvents` is main-thread only; `SDL_PollEvent` can pump. Host must translate exception/error to typed reason, not raw Windows pointer or unbounded system error text. Shutdown and restart avoid leaking HWND, GPU resources, input capture, COM or WASAPI endpoint handles.

## 4. Window, DPI, multi-monitor, focus and accessibility
- Prefer system **Per-Monitor DPI Awareness v2** in app manifest (actual activation evidence required) and SDL3 content/pixel scale semantics. Windows SDL logical window coordinates may use *physical pixels* with separate content scale; use SDL3's `SDL_GetWindowSizeInPixels`, display content scale and window scale, not an incorrect universal x2. In each window report **content scale, pixel density, framebuffer extent and DPI revision** independently. `WM_DPICHANGED` suggested rect is informational until owner accepts/resizes; preserve window restore geometry in monitor-safe units.
- Handle move between monitors at 100%/125%/150%/200%, monitor attach/detach, rotation, RDP reconnect, HDR<>SDR, resolution/DPI change, taskbar scaling, UI font re-rasterization, pointer hit-test alignment and position clamp; no edge/mouse double scaling.
- Window states: CREATING, VISIBLE, FOCUSED, OCCLUDED, MINIMIZED, RESIZING, SUSPENDING, DESTROYING, LOST with monotonically increasing **WindowEpoch**, no stale HWND usage. Handle `WM_SIZE` zero-dim, DWM occlusion, Alt-Tab, borderless fullscreen, recovery after display/GPU changes, no unbounded render allocation on drag-resize.
- Text/IME composition and clipboard belong the UI/CORE-01 layer, **not GAME-01 gameplay buttons**. Keyboard layouts, AltGr/dead keys, surrogate pairs/Unicode composition, touch pen accessibility, onscreen keyboard and screen-reader interaction must be addressed in owner UI/OS adapters. No global hooks or password capture.
- Focus loss/device disconnect/power suspend releases every stuck key/button/axis state through GAME-01 DeviceEpoch semantics; pointer lock/cursor capture revoked and restored safely. Windows security privileges UAC prompts must never be bypassed by app/game agent.

## 5. Graphics surface and presentation policy
- PLAT-01 exposes **WindowsPresentSurfaceV1** (opaque WindowId/WindowEpoch, extent px, scale/DPI, display capability, format/color space/HDR hints, preferred mode) to GFX-01. It does not own Vulkan/D3D12 native device or resource handles, shader compiler, MSAA resolve, render passes or GPU debug API.
- Compare Vulkan Windows native WSI surface and D3D12/DXGI swapchain **only as candidates**. DXGI flip `FLIP_DISCARD`/`FLIP_SEQUENTIAL` recommended for Windows direct presentation; tearing/VRR contingent on feature query plus proper sync interval/flags; never assume every device or Windows version supports. Borderless fullscreen preferred evaluation over exclusive for modern DWM; do not promise equivalent latency without actual data.
- GFX-01 owns backend capability selection and feature tier. Negotiate HDR10/scRGB/SDR, color gamut, swapchain resize/generation and present queue; user monitor toggles trigger distinct presentation epoch. Avoid mixing GPU timestamp and present time. High-refresh, multi-GPU/hybrid adapter selection and external GPU unplug require exact capability readback; `DEVICE_LOST` may require controlled restart, never fabricate universal rehydrate.
- MSAA swapchain may need resolved intermediate buffer; DXGI flip model does not support MSAA swapchain directly. Present must stop on zero-sized/occluded surface, avoid busy spin and power drain; explicit frame/presentation receipts with status `PRESENTED`, `SKIPPED_OCCLUDED`, `SURFACE_STALE`, `DEVICE_LOST`, `RESTART_REQUIRED`.

## 6. Input, GameInput, event and OS security
- Native event selection **SDL3 as preferred CORE-01 host candidate** (zlib) with Win32 supplemental per-platform bridge if proven needed. GameInput v1+/v4 optional Windows controller capabilities; latest PC runtime/redistributable depends on NuGet/MSI or v4 side-loaded DLL terms. Do NOT assume GameInput SDK/GDK is free-to-redistribute without reading exact package license and installer contract, or that Xbox console entitlements follow PC support.
- SDL3 `SDL_PumpEvents` main thread; do not install new PLAT input loop. Normalize Windows scan vs logical key, physical vs text/IME, mouse relative/absolute, gamepad XInput/GameInput/SDL mapping, hotplug and haptics capability. Avoid duplicate events from SDL3+GameInput: source-priority/dedup and stable DeviceEpoch. No globally recording HID identifiers.
- Touch/pen tablet and high-frequency pointer are explicit capabilities with truthful `UNSUPPORTED` if no test coverage. GAME-01 context focus/rebind/seat ownership handles gameplay behavior, not PLAT. Replay in sandbox fixtures, no live input injection from LLM/MCP.

## 7. Audio, filesystem, desktop and process integration
- Windows audio through AUD owner and available endpoint plugin: investigate WASAPI shared/event-driven, optional XAudio2/miniaudio, OS device hotplug, exclusive modes and spatial output under license and measured latency; PLAT-01 only provides Windows endpoint capability and lifecycle. **No blocking filesystem/COM/logging from realtime callback**. Owner must distinguish device loss from audio silence or missing endpoint; only after actual callback proof claim underrun-free behavior.
- Windows data roots and file picker via scoped DATA-01 and UI owner: project path permissions, Unicode UTF-16 API conversion, drive/network/OneDrive reparse and junction traversal, long paths, restricted directories, UAC/ACL, save under LocalAppData/RoamingAppData vs project root by owner policy. No arbitrary native path surfaced to agent. Use atomic file/journal only as proven by DATA source owner, no blanket cross-filesystem atomicity.
- OS service integration: sleep/hibernate/resume, low-memory notifications, timezone/time changes distinct from monotonic tick, window focus and notifications (only if appropriate), accessibility high contrast/reduced motion. Runtime background telemetry and auto update network disabled without explicit user consent and separate capability.
- Security: strict DLL load search allowlist, signed vendor binaries and Secure DLL search; reject plugin/DLL from untrusted cwd/asset folders. Process **least privilege/no admin by default**, UAC for installer only if approved. Bounded file dialogs, no arbitrary shell powershell script from project/AI. Control COM apartment/thread and third-party native memory API lifetime.

## 8. Packaging, signing, updates and licensing responsibility
- **BIZ-03** owns installer/update/uninstaller/rollback and public release gates, PLAT-01 emits Windows-specific `WindowsDistributionPlanV1`: unsigned internal portable zip/exe for smoke vs packaged MSIX vs unpackaged EXE/MSI for owner-approved distribution. No production signing identity or Store publication assumed.
- MSIX provides package identity/deployment graph and reliable install/uninstall but package capability, runtime dependency, virtualization and desktop extension policies differ from unpackaged Win32. Windows App SDK 2.x optional; framework-dependent packaged needs framework dependency, unpackaged requires bootstrapper/dynamic dependencies; do not add Windows App SDK runtime to a pure SDL Win32 app by default. C++ redistributable/CRT choice and Windows SDK/compiler version must be pinned/verified.
- Smart App Control/AuthentiCode signature and publisher reputation require real trusted signing and distribution policy. Unsigned development binaries may be usable under explicit test configuration, **cannot be equated with public production readiness**. No certificate purchase/Store fee/paid API without owner approval.
- Code signing proves publisher and bytes, not safe runtime. Real update channel must independently verify package signature/hash/rollback and use BIZ-03 update authority. No automatic update triggered by PLAT-01.
- SDL3 root zlib (notice), potential GameInput redistribution/license, DirectX Agility SDK redistributable terms, Windows SDK/toolchain/Microsoft Windows App SDK license, Vulkan loader/layers, miniaudio and third-party codecs each require exact-tag SBOM/NOTICE/CVE analysis. NLE-D009 engine source license still OPEN.

## 9. Required future Windows smoke plan
Candidate hardware matrix to ratify: Windows 11 serviced x64 desktop low-tier iGPU/old discrete; mainstream GPU AMD/NVIDIA, hybrid iGPU+dGPU laptop with mixed-DPI monitors; 60/120/144+ Hz and HDR optional; audio default+USB/BT endpoint; keyboard layouts ABNT2/US and GameInput/XInput/SDL gamepads; clean user account and non-admin install; RDP/remote/VM negative capability only. Win ARM64 and Windows 10 LTSC optional if owner approves.
1. Clone frozen source SHA and toolchain lock; build Editor.exe + Game.exe with pinned MSVC/Clang-cl/GCC where supported, x64 Debug and RelWithDebInfo release with symbols and SHA, optionally native ARM64 build under separate target.
2. On clean supported OS hardware with no dev SDK, launch Editor and one *rights-clear synthetic* exported game, inspect version/manifest, create/resume window, CPU-only headless if supported, route keyboard/mouse/gamepad and licensed audio, display 2D/3D validated source scene via GFX owner.
3. Resize/move multi-monitor, minimize/restore, Alt-Tab, GPU device lost/recovery, controller disconnect, audio device switch, sleep/resume. Record actual OS/hardware/GPU driver, GPU feature tier, `WindowEpoch`/`DeviceEpoch`, owner receipts and bounded local CORE-06 traces.
4. Distinguish **build smoke** from **packaging/install/signed distribution**. Real live hardware gate is mandatory to claim support; GitHub Windows hosted runner compiles and headless sanity, not an oracle for real GPU/audio/monitor hardware. No invented build/latency/compatibility evidence.
