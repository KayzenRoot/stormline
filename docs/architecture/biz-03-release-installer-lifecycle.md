## Product ownership and minimum end-to-end lifecycle
The core user-facing invariant is *install, export, update and reverse on qualified target without developer intervention*, while preserving independently authored projects/saves. Separate the distribution of **editor/SDK**, **exported game**, **optional browser-hosted build**, **runtime/dependency redistributables** and **user-created content**, each with independent rights and recovery boundaries.

## Proposed immutable release state machine
`INTERNAL_DRAFT -> CANDIDATE -> QUALIFYING -> RIGHTS_AND_SECURITY_REVIEW -> OWNER_APPROVED -> STAGED_CHANNEL -> GENERAL_AVAILABLE -> DEPRECATED -> RETIRED`; rejection to `BLOCKED/REVOKED`. **No current state reached for any Stormline binary**. A channel pointer is a signed/verified mapping to one immutable artifact digest and target matrix, never a mutable unverified "latest" URL. Explicit rollback to *older approved digest* requires a **new owner-authorized signed release-channel revision**; it must not bypass updater anti-rollback/version floor. Rollback of application executable must not forcibly downgrade a migrated user project/save schema.

### Proposed native packages, conditional on rights/qualification
- **Windows:** MSIX with Store signing as a possible platform route vs independently signed sideload MSIX or signed MSI/EXE. MSIX identity/update semantics differ from MSI upgrade codes and EXE custom installers; users must not receive conflicting auto-update mechanisms for one installation. Exact Windows versions, GPU/CPU, VC runtime and x86_64/ARM64 have independent qualification. Do not claim Microsoft Store re-signs arbitrary MSI/EXE; for Store MSI/EXE program actual CA-trusted Authenticode + immutable HTTPS version URL/silent install applies. No certificate/account is currently approved.
- **macOS:** signed `.app` via Developer ID with Hardened Runtime, entitlements, notarization via `notarytool`, offline stapled ticket when channel requires; DMG/PKG ownership and user-install protections. Sparkle 2 (MIT as upstream candidate) can implement macOS authenticated update appcast with EdDSA, but only if it composes with TUF-style trust, not a second uncoordinated source of truth. App Store distribution uses separate signing and review. macOS arm64 target native, Intel conditional; certificate/Apple account cost is an **external gate**, NOT "$0 ensured".
- **Linux:** per-target `tar.zst` portable option for internal testing, **Flatpak** + repository/OSTree ecosystem or conditional AppImage; `.deb`/`.rpm` only if maintainable and signed repo upgrade/uninstall/ownership documented. No universal Linux binary due to glibc/libstdc++/FUSE/Wayland/X11/GPU differences. Security fixes follow selected channel; honor package manager ownership and avoid second embedded updater competing with it. Sign repo metadata / validate Flatpak refs and pin exact dependency/runtime baselines.
- **Browser:** immutable content-hashed JS/Wasm/asset manifests from PLAT-05, HTTPS, CSP, COOP/COEP as target requires, HTTP cache-control and service-worker cache versions/atomic activation. **No native installer** for browser games, no assumption PWA installation required. Prevent stale service-worker mixing game JS and assets; never cache creator private project data to public origin. Browser deployment/hosting costs and security ownership are separate gates.
- **SDK and redistributables:** BIZ-02 future SDK signature+ABI/version rules, SDK samples original and separately rights-cleared, no implicit sublicense of engine/plugin DLL or third-party runtimes. Each exported game carries exact licenses/notices and manifest verifying permitted redistributable set.

## Updater and rollback threat model
Threats include compromised CDN, HTTP or DNS, mirror replay, key theft, metadata expiry freeze, version rollback, mix-and-match between platform chunks, downgrade into exploited binary, content-hash collision assumptions, symlink/path traversal, decompression bomb, TOCTOU between verification and installation, MITM through local proxy, partial writes, power loss, concurrent launch/update, store re-signing and credentials in CI. A **TUF-inspired / formally specified updater trust root**, not a claim of TUF implementation: root key threshold/rotation, delegated targets, snapshot and timestamp roles, target digest and length, monotonically tracked signed metadata version/freshness, pin allowed target, platform/arch feature and channel. HTTPS alone or SHA256 downloaded from same compromised page does not establish authenticity. Never expose signing private keys to arbitrary untrusted fork PR. Need independently audited key management and real threat tests.

### Crash-safe transactional installation
A future updater stages complete verified content under same filesystem/volume where possible; checks disk-space and permission; fsyncs payload and metadata/directory as platform permits; validates executable eligibility and immutable receipt before atomic rename/symlink/junction/APFS/OS package-manager activation; maintains last-known-good version and journal+recovery marker. Cross-volume "atomic" rename is NOT guaranteed. Native OS/system installers may own commit and rollback, so never force homemade filesystem swaps into protected app bundles. On failed boot health check auto-quarantine new executable, controlled fallback only if compatible with user data schema and integrity; otherwise REPAIR_REQUIRED with no data damage. Uninstall never removes creator-owned projects/saves by default; optional explicit backup/exported data removal with consent is separate.

### Migration of source project and saves
App binary version, editor project format, data migration schema and game save version are **distinct version axes**. Migration is a typed `PREVIEW -> CONSENT -> SNAPSHOT -> STAGE -> VALIDATE -> COMMIT -> READBACK` owned by DATA-04/project owners, with semantic comparison/checksum and migration journal; BIZ-03 routes owner workflow only. Irreversible migration creates recovery receipt and requires compatible backup and opt-in, no automatic downgrade of source to old schema. Every migration is tested with corrupted data, concurrent edits, disk full, crash at each commit barrier, schema N-1/N, stable object IDs and cross-platform path portability. Secrets and private player data stay local/private and out of CI fixtures unless independently consented.

## Channels, support and measurements
Channels INTERNAL (nonpublic), controlled CANARY/BETA only after owner-approved product gating, and PUBLIC_STABLE only after *complete* v1.0 DoD and licensing/rights/QA/hardware qualification. Cohort assignment via opt-in stable opaque pseudonymous ID or no tracking; channel promotion signed and auditable, pause/revoke/rollback must stop rollout rapidly. Never silently downgrade private game projects. Support: compatibility/requirements table, release manifest and changelog, known issues/severity window, security patch SLA proposal (threshold TBD), vulnerability disclosure, anonymized crash reports opt-in default-OFF, retention/export/delete rights (LGPD/GDPR applicability legal review), accessiblity and localized installers.
Future metrics: installation success by real platform, p50/p95/p99 update time/bytes, retries and bandwidth, build-to-release lead time, disk usage, crash loops/repair, update availability offline, user-impact and project preservation. No thresholds are preapproved, and no real samples/builds have run.
