## 1. Product acceptance and proof semantics
Catalog: **"Índice incremental de cenas, scripts, assets, referências, docs e schemas para agentes."** Acceptance **"Consultas filtradas com contexto mínimo e atualização incremental."** A future real authorized query for a named scene, script symbol, asset, document or schema must return correct *scoped* typed references, compact sourced excerpts and freshness receipts, after a **single source update without unrelated full-project reindex**. No context leakage outside requested grants. Prove both search quality (relevance/recall), freshness/revision, bounded index cost and minimum byte/token context across native/headless targets, not just index table existence.

**Architectural rule: AI-02 is a **rebuildable semantic read projection**, never a new canonical project database, asset registry, scene graph, script parser, document editor, authoring command bus, AI search service or vector store with privileged file access.**

## 4. Logical model: source vs projection, index lifecycle
Proposed typed logical rows, not SQL tables or approved ABI:
- `SemanticEntryV1`: opaque `ProjectId`, `EntryId` (stable projection key, scoped by source `AssetId/SceneId/ScriptModuleId/DocumentId/SchemaId`, revision and symbol/nested path), `EntryKind` (SCENE, PREFAB, ENTITY, COMPONENT, SCRIPT, SYMBOL, ASSET, MATERIAL, AUDIO, TEXTURE, DOCUMENT, SCHEMA, COMMAND_DESC), canonical owner ID/revision/digest, owner capability scope, display label normalized under versioned text policy, owner source locator with safe revision, summary/chunk offsets only if allowed, content rights classification.
- `SemanticEdgeV1`: source EntryId -> destination EntryId, `EdgeKind` (REFERENCES, CONTAINS, INSTANCE_OF, OVERRIDES, IMPORTS, DEPENDS_ON, DOCUMENTS, SCHEMA_FOR), owner-provenance and revision. DATA-02 `DependencyEdgeV1` remains authoritative for asset dependencies. Other scene/script edges are **projections of owner records**, never AI-02 truth.
- `IndexGenerationV1`: project scope, index schema/tokenizer version, source OwnerSnapshotSet digest/manifest, last applied committed change sequence per owner, content policy version, build generation, state, checksum, index bytes/count, diagnostic drops and availability. A snapshot token does not authorize access by itself.
- `IndexChangeEnvelopeV1`: owner-verified `SOURCE_COMMITTED` with OperationId, ProjectId, source type/stable ID, from/to revision, owner source digest, change set, dependency impact and tombstones; no unversioned filesystem-watch event as authority.
- `IndexQueryV1` and `IndexQueryReceiptV1` defined in API; bounded result fields, stable sort/cursor, context budgets and source verification.

Proposed states `UNINITIALIZED -> SOURCE_SCANNING -> BUILDING -> VERIFYING -> READY`; during change `READY -> DIRTY -> APPLYING -> VERIFYING -> READY`; failures `STALE/REBUILD_REQUIRED/RECOVERING/CANCELLED/FAILED_UNAVAILABLE`. Last verified generation may be read **only** when caller's freshness policy permits its source revision and ACL revision. Index cache missing/corrupt must never block canonical DATA-02/DATA-04 reads nor mutate project source.

## 5. Incremental updates, exact revision fences and crash recovery
A file watcher is only a **hint**; it cannot establish a DATA-02 AssetId/SourceRevision, DATA-04 commit or scene truth. On owner `SOURCE_COMMITTED` receipts, record project/owner sequence and changed IDs. Derive dirty set using stable-ID dependencies, bounded reverse-graph traversal, tombstones and schema/parsing policy. Coalesce bursts and deduplicate OperationIds; no full project rescan on every keystroke. On rename/move preserve AssetId and references; on reimport source revision changes and dependent projections invalidate; on duplicate new AssetId/EntryIds; delete/tombstone remove indexed contents even from FTS postings. Cycle-safe dependency traversal with max depth/fan-out/time and typed `PARTIAL_REINDEX`.

Atomicity claim limits: owner DATA-02 canonical metadata and DATA-04 source/journal can commit independently of AI-02 derived search. `SOURCE_COMMITTED_INDEX_PENDING` is a **true** state; do not mark `INDEX_READY` until derived generation applied, index integrity verified and readback successful. If crash after source commit and before index flush, recover by replaying verified committed OperationId/sequence or bounded full rebuild; cursor gaps, schema/ACL policy change or integrity mismatch trigger rebuild. Derived cache may be safely discarded; losing canonical sidecars/AssetIds is NOT recoverable by an index rebuild.

**Freshness modes:** `REQUIRE_AT_LEAST_SOURCE_REVISION` (wait within budget for owner source fence or explicit `INDEX_STALE`), `SNAPSHOT_EXACT` (pinned complete owner snapshot set and generation, expire/deny if gone), `ALLOW_STALE_WITH_PROVENANCE` (readonly stale labeled, if ACL permits). No unbounded wait, no fake read-your-writes and no unqualified `latest`. Source and index revision vectors may be partial across owners, therefore no invented globally atomic project snapshot. A query must declare coverage/partial owner status.

## 6. Query semantics: exact IDs, text, graph, hybrid, minimum context
1. **Authorize first:** authenticated ProjectId/actor grant, allowed EntryKind, field projection, privacy/rights, allowed owners, version and ACL/policy revision. Index hits are **not** authorization; recheck each selected owner reference before excerpt or graph expansion.
2. **Plan bounded query:** typed filters for kind, asset type, tag, revision, dependency edge depth, source path alias, module/symbol, text terms, exact ID, owner schema/capability; normalize Unicode with version; reject raw SQL, arbitrary regex, filesystem glob escape, unaudited embedding or call to external LLM.
3. **Candidate retrieval:** exact IDs and structural owner refs first; lexical FTS + structured metadata, optionally graph neighbor expansion within ACL. Rank with stable deterministic tie breakers and revision/coverage metadata. Do not call BM25 score a calibrated probability.
4. **Hydrate minimal owner-approved content:** typed source citation/locator/revision, short snippet with bounds and redaction; avoid entire file/scene/source graph, raw credentials, private path or unpublished copyrighted/third-party content.
5. **Cap context:** caller-defined `max_rows`, `max_bytes`, `max_estimated_tokens`, `max_snippet_chars`, `max_graph_depth`, `max_edges`, deadline/CPU budget. Count actual bytes and **token estimate is provider-agnostic, approximate unless specific model tokenizer pinned**. If budget exhausted, emit `PARTIAL_BUDGET`, stable cursor and counted omissions; never silently truncate a JSON structure.
6. **Stable pagination:** keyset `(score_bucket, kind, stable EntryId, revision)` with explicit fixed scoring policy and snapshot generation. Opaque continuation bound to ProjectId+principal/grant or policy hash+query normalized digest+sort+snapshot generation+expiry; HMAC/signature only if owner-approved local secret/key policy. A cursor is not bearer authorization and must not outlive ACL change.
7. **Completeness and ranking:** report coverage owner kinds, indexed source commit watermark, matching permissions, missing/unsupported owners. Query results cannot claim full recall when part of source isn't indexed. Exact ID match and owner references outrank fuzzy text; vector similarity only separate OPTIONAL future research with demonstrated accuracy/security benefits.

Consider FTS5 `unicode61` vs trigram and per-language tokenization (Unicode version, case fold, diacritics, mixed CJK/code symbol punctuation). Trigram does **not** index 1–2 char substrings effectively: disclose fallback/cost. Case-insensitive filesystems aren't asset identity; join only typed ProjectId/AssetId.

## 7. Technology direction and important pitfalls
**Candidate** DATA-02 SQLite-derived asset index may be extended with per-project FTS5/metadata/edge materialized projections, using tables separate from canonical DATA-02 records and **the same rebuildable cache policy**; avoid second SQLite DB claiming AssetId truth. FTS5 external-content mode needs careful trigger/update order and backfill: just adding triggers doesn't index existing rows; corruption/stale content requires explicit `integrity-check` / `rebuild` with owner source manifest comparison. Evaluate contentless-delete tables version and feature availability; SQLite FTS5 default `unicode61` is based on Unicode 6.1, not latest Unicode segmentation by default. SQLite WAL permits readers+writer snapshot isolation but long-running readers can starve checkpoint and grow WAL; bound readers/pagination/checkpoint and measure disk. No SQLite WAL on unsupported network filesystem.

Alternative evaluated: pure C++ in-memory inverted index, Tree-sitter incremental parse for script symbols (only against GAME-02 approved source/grammar/rights), Tantivy/C++ bridge, Xapian GPLv2+ licensing, vector/embedding retrieval as future prove-or-drop, cloud services out of default scope. No parser/database/embedding SDK selected or installed.

## 8. Threat model, performance and scope
- **Security:** cross-project or multi-tenant leak through FTS postings, counts, ranking or cursor; revoked grant; stale ACL; malicious prompt injection in indexed documents; private comments/paths; untrusted regex/SQL/FTS query syntax; token budget DoS; symlink/traversal through untrusted docs; stale source code snippets; embedding inference exfiltration. Fail closed, escape text as data, authenticate before query and hydrate, field-level owner filtering, no remote upload.
- **Consistency:** source/index race, partial owner revision vectors, delayed fsync, contentless FTS deletes, schema migration, tokenizer changes, deleted/tombstoned assets, rename, import churn, crash and WAL growth. Require typed error and no false freshness; rebuild from verified source.
- **Perf:** cold full build vs incremental single edit cost, FTS query p50/p95/p99, 1k/100k/1m assets+scenes+docs, CPU/heap/disk/WAL, high-churn reimport, multi-agent 32 readers/writer, CJK/emoji, index overhead vs source. No numeric claims until representative native Windows/Linux/macOS/Apple Silicon/headless/Web adapter tests. Ranking quality `recall@k`, `MRR`, `nDCG@k` on human-labeled relevant sets; minimum-context measured bytes and optional pinned-tokenizer tokens. Partial provenance is explicit.
- **NECESSARY** research: owner-derived stable ID graph, incremental invalidation/fences, authorized bounded structured and lexical query, snapshot/cursor, rollback/rebuild, security/licenses, 128 tests and benchmark. **IMPORTANT** future consideration: dependency graph explanation, symbol navigation/source map, multi-owner coverage and bounded snippets. **FUTURE:** semantic embeddings, RAG rerank, vector ANN, AI summaries, cross-workspace federated search, cloud search, collaboration/real-time search sync. **OUT OF SCOPE:** any code, SDK, new canonical DB, arbitrary source execution, raw SQL/host paths, network services, owner grant approval, chosen engine license, benchmark results, and unlocking implementation #76.
