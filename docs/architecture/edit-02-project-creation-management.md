## 4. Proposed project creation transaction and crash consistency
### Four-stage create (design, not functioning)
1. **PREVIEW**: validate editor principal/capability, requested mode, safe project display name (Unicode case/normalization collisions), target/root creation grant, template hash/version/license and dependency closure from local catalog, required GFX/WORLD capabilities, OS path restrictions, disk quotas; present immutable plan and effects. No files written, network fetched or shell executed.
2. **STAGE**: use CORE-01/DATA-01 **handle-relative no-follow** creation in a unique private sibling temp directory **on same local filesystem/volume as target**, with restrictive ACL, random nonce, optional staging manifest/checksum and bounded files. Never overwrite an existing target. Verify file count/size/path depth/links and expected content digests. Commit marker written only after files and descriptor validation, actual persistence barriers chosen per OS/filesystem.
3. **VALIDATE**: parse staged descriptor/schema and all template files, validate references/capability and no symlink/hardlink escape, ensure immutable source/destination root handles still refer to approved directories; ensure free space/permission/short-name conflict. Do not run template hooks/gradle/npm/plug-in code or pull remote packages implicitly.
4. **COMMIT**: same-volume atomic **rename into an absent destination** under owned root where supported; flush staged data + directory entries and parent as OS/filesystem allows, then publish recent-project entry via separate idempotent CAS. A local rename is **not a distributed transaction**, durability against sudden power loss/remote FS cannot be guaranteed without actual audited OS+hardware tests. On unsupported atomic rename/ACL/share violations => explicit fail-closed/recovery path, not unsafe copy-over target.

On process crash, discover incomplete hidden staging with owner marker; verify signed/hashed local manifest before offering **resume/recover/discard** with explicit user consent and quarantine; do not blindly delete/rewrite a previously valid target. Any partial directory is marked INCOMPLETE and never opened as a valid project until verified committed. Idempotent retry by operation ID, no duplicate project identity or overwritten existing tree. Project creation includes real filesystem effects in future only; no such effects now.

### Upgrades/restore and source control
- **READ_ONLY_COMPATIBLE** when newer format can be inspected without loss; **UPGRADE_REQUIRED** only with enumerated steps, backup, dry-run semantic diff, space and referential-integrity check. Reject ambiguous downgrade. Upgrade orchestration is EDIT-02, actual schema transforms DATA-04 owners.
- Future upgrade stages **copy-on-write** with immutable pre-upgrade snapshot, migration graph old→new each step with expected revision, integrity check and complete swap/commit marker, preserving source until verified; rollback or roll-forward must be deterministic, not silent force-close. For large files, snapshot hardlinks need copy-on-write safety proven, not assume hardlinks are isolated backups.
- Crash at each stage, power loss, ENOSPC, permission revoked, locked/open files, antivirus interference, rename conflict and log failure must yield recovery receipt. Windows/NTFS/macOS APFS/Linux ext4/Btrfs and network/cloud-sync folders are not equivalent; **SQLite WAL is not supported over multi-host network filesystems** and `synchronous=NORMAL` WAL can lose latest acknowledged commit on power loss. Any SQLite cache/index choice requires durability decision. Never claim `fsync` covers all hardware unconditionally.

## 5. Threat model, sandbox and path identity
Untrusted path, template archive, manifest, plugin, dependency URL, imported project and MCP request may be adversarial. Threats: `../`, absolute path/drive/UNC, NUL/reserved Windows device names/ADS, Unicode NFC/NFD and case-insensitive collision, trailing dot/space, symlink/junction/reparse mount escape, TOCTOU swap after validation, cross-volume rename, sparse files, ZIP-slip/tar path traversal, link/hardlink escapes, decompression bombs, oversized/recursive JSON, duplicate IDs, malicious post-install scripts, remote URL SSRF and secret exfiltration. **Reject or require explicit trusted boundary**.
- Use DATA-01 granted root **directory handles** and OS-specific component-by-component no-follow resolution; Linux `openat2` `RESOLVE_BENEATH`/`RESOLVE_NO_SYMLINKS` when available, macOS safe `openat`/`O_NOFOLLOW`/file IDs, Windows reparse-point-aware handle validation (symlink/junction), combined with atomic target create. Recheck identity at commit; **string canonicalization or checking then opening is insufficient**. Hardlinks/volume mount/device nodes and archive link entries need explicit policy. Unsupported secure path operation => deny.
- Cap archive uncompressed total bytes, member count, compression ratio, path depth, nesting and extraction time before/during extraction; no shell extraction, no runnable template hook, no dynamic code execution from untrusted project metadata. Template trust store/digest and license/SBOM separate; **a signed archive may still contain vulnerable or unsafe content**.
- Prevent per-user recent-project list/path leakage to logs, AI/MCP or exported zip. Permissions are scoped by project, expected source CAS, operator confirm for overwrite/migration/external network. No implicit cloud sync, paid vendor or repo clone.
