# Architecture (conceptual)
Status: PROPOSED / NOT IMPLEMENTED

## Organização candidata
Applications (Editor / Client / Server / Test harness)
-> Public Engine API + World Runtime
-> Renderer, Physics, Animation, Audio, Networking, Terrain/Streaming, VFX
-> Core services (memory, jobs, logging, time, I/O, diagnostics)
-> Platform abstraction (Windows/Linux, CPU/GPU/OS).

## Princípios
- Engine própria; bibliotecas especializadas são dependências substituíveis quando isso tiver valor demonstrável.
- Servidor sem GPU/UI obrigatória; editor não deve controlar o ciclo de vida da simulação.
- Contratos explícitos para ownership, serialização, ID estável, tempo, coordenadas, assets e plugins.
- API pública não deve expor tipos de terceiros indiscriminadamente; evitar abstração sem evidência de necessidade.
- Tempo de simulação desacoplado do render; políticas de fixed step a definir.
- Posição global vs local, precisão de mapas grandes e origem deslocável a avaliar.
- Testabilidade e ferramentas de profiling desde o início.

## Stack candidato; NÃO aprovado
C++20, Vulkan, SDL3, Jolt, EnTT, miniaudio, glTF, meshoptimizer, Python, CMake, compilador de shaders e biblioteca de transporte sob avaliação. Matriz de licença, versão, suporte, performance e complexidade precede escolha definitiva.

## Pesquisa de inovação
Renderização e iluminação, VFX, áudio e hardware modesto merecerão ADRs e experimentos independentes; provar ganhos visuais e eficiência em cenas comparáveis. Não declarar tecnologia inédita sem pesquisa de anterioridade.

## Proposta AI-first em avaliação
A nova direção de produto exige avaliar um **Command Kernel** comum ao editor, CLI/headless e adaptador MCP, com contratos estáveis e auditáveis. Esta orientação está descrita como proposta em [AI/MCP Contract](product/ai-mcp-contract.md), não como sistema já projetado/implementado. A revisão técnica deverá considerar a especificação MCP 2026-07-28, backward compatibility, ferramentas/resources/prompts e segurança por capability/permission.

## CORE-01 — Platform & Lifecycle (pesquisa técnica PROPOSTA)
A direção preferencial de pesquisa é C++20 + SDL3 + CMake Presets/Ninja, com Win32, Wayland/X11 e Cocoa/Objective-C++ encapsulados em bridges estreitas quando necessário. A interface de host deve funcionar também sem display/GPU. SAPL (capability graph + event journal) é hipótese a medir, e **não** inovação comprovada. A decisão está apenas PROPOSED em [ADR-0003](adr/0003-core-01-platform-technology.md), com [contratos de plataforma](architecture/core-01-platform-lifecycle.md) e [matriz de tecnologias](research/core-01-platform-technology-matrix.md). A escolha gráfica Metal/Vulkan/D3D12 pertence a GFX-01, fora desta WO.

## CORE-02 — Memory & Allocators (pesquisa PROPOSTA)
Arquitetura de memória C++20 `std::pmr` com ownership, domains e budgets versionados; comparadores `malloc/new`, mimalloc e rpmalloc antes de qualquer substituição global. Hipótese de inovação `Stormline Memory Fabric` restrita a políticas e diagnósticos mensuráveis, não um malloc reinventado. Ver [CORE-02](architecture/core-02-memory-allocators.md), [matriz](research/core-02-memory-technology-matrix.md), [ADR-0004](adr/0004-core-02-memory-policy.md). GPU VRAM pertence ao módulo GFX-03. Nenhuma tecnologia de produção aprovada sem benchmark.

## CORE-03 — Jobs & Concurrency (proposta de pesquisa)
Scheduler de tarefas, execução paralela e work stealing com contratos de duração/cancelamento de jobs, afinidades, deterministic commit e quotas para hardware de poucos núcleos. Candidatos: C++20 `std::jthread`, Taskflow, enkiTS e oneTBB; avaliar Stormline Frame-Aware Scheduler somente se superioridade funcional/operacional for demonstrada. [Spec](architecture/core-03-concurrency-jobs.md), [matriz](research/core-03-technology-matrix.md), [ADR-0005](adr/0005-core-03-jobs-concurrency.md). Sem código ou benchmark.

## CORE-04 — Time & Simulation Clock (research proposal)
Monotonic C++20 steady_clock adapter with injected fake clock, rational integer fixed tick timeline, explicit pause/single-step/interpolation and bounded catch-up policies for offline/server modes. Tick ordering and numeric physics determinism are separate obligations. [Architecture](architecture/core-04-time-simulation.md), [technology matrix](research/core-04-technology-matrix.md), [ADR-0006 PROPOSED](adr/0006-core-04-time-policy.md). No implementation or benchmark.

## CORE-05 — Math, Coordinate Spaces & Types (research proposal)
Portable C++20 typed math and scalar reference, GLM as candidate comparator, strong units, right-handed +Y-up world, explicit 2D/UI/graphics adapters, global f64 or cell+local f32 origin shifting, stable persistent IDs distinct from runtime handles. [Architecture](architecture/core-05-math-coordinate-types.md), [matrix](research/core-05-technology-matrix.md), [ADR-0007 PROPOSED](adr/0007-core-05-coordinate-policy.md). No engine code or numeric performance evidence.

## CORE-06 — Diagnostics & Observability (research proposal)
Event/span/counter/crash envelopes, build SHA + frame/tick/job correlation, bounded offline-first logs and redacted diagnostic export. Prefer evaluating spdlog for logging, Tracy for development profiling, Perfetto for offline traces, Crashpad as conditional native crash candidate; no cloud/listener/automatic telemetry. Stormline Diagnostic Fabric (SDF) is a prove-or-drop research hypothesis only. [CORE-06 Architecture](architecture/core-06-diagnostics-observability.md), [Technology Matrix](research/core-06-technology-matrix.md), [ADR-0008 PROPOSED](adr/0008-core-06-observability-policy.md). No library is installed or runtime profiled.

## DATA-01 — Virtual File System (research PROPOSED)
Scoped virtual namespaces/mount permissions, deterministic overlay priority, typed `VfsPath` and file handles, read-only archive mounts, bounded I/O/cache, staged writes/recovery, and native handle-based security against TOCTOU/symlinks. Technology candidates: owned minimal mount table + C++20 `std::filesystem` baseline, PhysicsFS zlib and libzip BSD-3-Clause (conditional). No real filesystem sandbox implemented or proven. See [Architecture](architecture/data-01-virtual-file-system.md), [research matrix](research/data-01-vfs-technology-matrix.md), [ADR-0009 PROPOSED](adr/0009-data-01-vfs-policy.md). AssetId belongs DATA-02; bundles/patching belong DATA-05.

## DATA-02 — Asset Registry & Metadata (research PROPOSED)
Persistent `AssetId` independent from file path/content hash/runtime handle, versioned revisions and provenance, dependency edge graph and query/impact contracts, semantic Editor/CLI/MCP operations and fail-safe recovery. Candidate: portable canonical metadata plus derived SQLite index (compare SQLite-authoritative and manifest-only), UUIDv7 vs v4, BLAKE3 vs SHA-256. Key risk is **DATA-01 VFS file updates cannot atomically commit as a single transaction with SQLite**; use staged journal and reconciliation as a future proof requirement. [Architecture](architecture/data-02-asset-registry.md), [tech matrix](research/data-02-asset-registry-technology-matrix.md), [proposed ADR-0010](adr/0010-data-02-asset-identity.md), [API contract](contracts/data-02-registry-api.md), [test matrix](testing/data-02-acceptance-matrix.md). No code, asset registry, database, schema or benchmark implemented.

## DATA-03 — Import & Conversion Pipeline (research PROPOSED)
Untrusted 2D/3D/texture/audio input goes through scoped DATA-01 VFS, bounded validation, semantic intermediate artifacts and DATA-02 stable AssetId/revisions, with receipt-backed idempotent reimport and explicit preservation/merge of user overrides. glTF/GLB baseline; compare fastgltf (MIT), cgltf (MIT), conditional Assimp (BSD-3-Clause-based), KTX-Software/Basis textures and advanced OpenUSD. **KTX-Software has mixed licensing and optional non-open-source ETC decoder:** exact file-level/license audit before vendoring. Source-to-runtime target cooking belongs DATA-05, scene format DATA-04. No network/host shell/MCP privilege; SIRG prove-or-drop R&D only. [Architecture](architecture/data-03-import-conversion-pipeline.md), [matrix](research/data-03-importer-technology-matrix.md), [ADR-0011 PROPOSED](adr/0011-data-03-import-policy.md), [API contract](contracts/data-03-import-api.md), [20 future tests](testing/data-03-acceptance-matrix.md). No importer code, decoder or benchmark exists.

## DATA-04 — Scene Serialization & Format (research PROPOSED)
Strict UTF-8 JSON scene authoring and a typed versioned SceneIR are **proposed**, separate from DATA-05 runtime cooked binary. Persistent scene/entity/component IDs and DATA-02 AssetId refs, explicit order and CORE-05 spatial rules, unknown optional fields preserved while required unknown components fail closed. ID-aware semantic diffs with three-way conflict preview and scoped Editor/CLI/MCP commands; staged, journaled migrations with prior-good restore, no false DATA-01 VFS + DATA-02 SQLite cross-system ACID assumption. Candidate JSON Schema 2020-12, nlohmann/simdjson, FlatBuffers/Protobuf/Cap'n Proto and RFC 8785/JCS restrictions require A/B conformance/perf and exact-tag license gates. SSD is prove-or-drop R&D, no code delivered. [Architecture](architecture/data-04-serialization-scene-format.md), [matrix](research/data-04-scene-technology-matrix.md), [ADR-0012 PROPOSED](adr/0012-data-04-scene-schema-policy.md), [API](contracts/data-04-scene-api.md), [future tests](testing/data-04-acceptance-matrix.md).

## DATA-05 — Target Cooking, Streaming Bundles & Safe Patches (research PROPOSED)
From DATA-03 intermediate receipts + DATA-04 scene IR and DATA-02 durable AssetId graph, cook **derived**, target-capability-aware immutable chunks and versioned manifests for Windows/Linux/macOS/Web/headless. Zstd/LZ4/Brotli, meshoptimizer geometry, KTX2/Basis textures and binary scene format are **candidates**, no version selected or installed. Chunk digests prove bit integrity, not publisher identity; remote updates require separate verified release trust policy. Progressive streaming must bound RAM, CPU, IO, GPU upload/VRAM and support HTTP range **fallback**; patches stage verified chunks and activate with recoverable generation journal, preserving last-good. DATA-01 VFS and DATA-02 registry are not one ACID transaction. Original SASG adaptive prefetch is a prove-or-drop research hypothesis, not implemented or measured. [Architecture](architecture/data-05-cooking-streaming-bundles.md), [technology matrix](research/data-05-cooking-technology-matrix.md), [ADR-0013 PROPOSED](adr/0013-data-05-cooking-policy.md), [semantic API](contracts/data-05-cook-bundle-api.md), [28 future scenarios](testing/data-05-acceptance-matrix.md).

## GFX-01 — Graphics Abstraction / RHI (research PROPOSED)
Stormline-owned thin C++20 RHI contracts for adapters/devices, feature tiers, generational resource handles, queues/barriers/fences, swapchain/offscreen/headless modes and device-loss recovery (or explicit restart-required). Compare native Vulkan (Windows/Linux), Metal (macOS), optional D3D12 (Windows), SDL3 GPU, bgfx and Dawn/wgpu-native WebGPU paths without choosing untested engine dependencies. **2026 Khronos guidance:** MoltenVK deprecated/community maintained, KosmicKrisp recommended on Apple Silicon; native Metal is independent baseline candidate; Intel macOS policy still open. Browser WebGPU is not universal and requires HTTPS, with PLAT-03-controlled WebGL2 degradation. World coordinates CORE-05 remain separate from RHI NDC/texture conventions. Shader compilation GFX-02 and render graph GFX-03 must not be duplicated. No GPU build, benchmark or renderer implemented; SCGF innovation prove-or-drop. [Architecture](architecture/gfx-01-graphics-rhi.md), [matrix](research/gfx-01-rhi-technology-matrix.md), [ADR-0014 PROPOSED](adr/0014-gfx-01-rhi-backends.md), [API](contracts/gfx-01-rhi-api.md), [28 future tests](testing/gfx-01-acceptance-matrix.md).

## GFX-02 — Shader & Material Compilation (research PROPOSED)
Versioned, compiler-independent ShaderDefinition/MaterialDefinition compiler-facing schemas, MaterialParameter and PipelineLayout reflection; compare **Slang**, HLSL/DXC, GLSL/glslang, shaderc, SPIRV-Tools/Cross, Tint/Naga, native MSL and WebGPU WGSL/WebGL2 fallback. Slang Metal is experimental and WGSL work-in-progress, so don't assume one production frontend spans all targets. Preserve DATA-02 AssetId, DATA-03 imported source, DATA-04 authored revisions and DATA-05 compiled immutable target artifacts; GFX-01 owns device/layout capability, GFX-03 GPU render graph, GFX-05 PBR and EDIT-05 material visual UX. Bounded source includes, deterministic variants under budget, strict reflection, cache keys with transitive source/compiler profile, and last-good generational hot reload / device-loss invalidation, with scoped Editor/CLI/MCP semantic commands and compiler sandbox requirements. Driver-native pipeline cache **not** portable. SSVF optimization hypothesis prove-or-drop; no compiler installed, shader compiled, GPU test or benchmark. [Architecture](architecture/gfx-02-shader-material-compilation.md), [technology matrix](research/gfx-02-shader-technology-matrix.md), [ADR-0015 PROPOSED](adr/0015-gfx-02-shader-compilation-policy.md), [typed API](contracts/gfx-02-shader-api.md), [30 future tests](testing/gfx-02-acceptance-matrix.md).

## GFX-03 — Render Graph and GPU Resource Manager (research PROPOSED)
Stormline-owned typed declarative Pass/Resource DAG with RAW/WAR/WAW subresource hazards, source-backed shader reflection and explicit imported/external/history state, deterministic topology, GPU barriers and cross-frame/async queue fence lifetimes. Transient memory alias requires proof of **actual GPU completion** (not just CPU DAG ordering) and compatible native heaps/format; conservative serial/no-alias fallback and explicit low-VRAM budgets for discrete/UMA/Web. Native candidates: Vulkan Synchronization2, GPUOpen VMA MIT; D3D12 legacy/enhanced barriers and GPUOpen D3D12MA MIT; Metal MTLHeap with hazard tracking/fences (untracked heaps can require explicit protection); browser WebGPU usage scopes and opaque memory budgets. GFX-01 owns native RHI primitives, CORE-03 CPU jobs, GFX-02 reflection, DATA-05 streamed assets, later visual modules own passes. Device loss/resize/hot reload invalidate GPU generation; Editor/CLI/MCP only semantic inspect/preview, never raw GPU pointers. Original SAFG is prove-or-drop, **no measured superiority**, and no engine code/GPU tests. [Architecture](architecture/gfx-03-render-graph-gpu-memory.md), [technology matrix](research/gfx-03-rendergraph-technology-matrix.md), [ADR-0016 PROPOSED](adr/0016-gfx-03-render-graph-policy.md), [API](contracts/gfx-03-render-graph-api.md), [34 future tests](testing/gfx-03-acceptance-matrix.md).
